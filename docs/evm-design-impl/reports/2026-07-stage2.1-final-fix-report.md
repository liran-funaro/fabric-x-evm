# Final review fix report — stage-2.1 batch-execution slice

Fixes four findings from the final review of the stage-2.1 batch-execution slice: C1
(Critical), M2, I1(a), and I1(b) (both Important). All four are implemented and verified.

## FIX C1 (Critical): an EVM ExecFailure must not abort the batch

**Problem.** `endorser/execution/executor.go`'s `runOn` treated any `ex.Send(tx)` error
other than `vm.ErrExecutionReverted` as a hard Go error. A committed-but-faulted
outcome — `*ExecFailure` (out of gas, invalid opcode, ...) — is exactly such an error, so
one out-of-gas tx in a batch aborted the *entire* batch (`ExecuteBatch`'s N==1 path, and
therefore also `Execute`, which is N==1's callee). Because `batch_executor.go`'s
authoritative pass only excludes `*TxRejected` (pre-execution rejections) and lets any
other error propagate, and because the gateway executor re-drains the same pending pool
every cycle, this permanently wedges the gateway on the first out-of-gas tx it sees.

**Fix.** Added `committedFaultStatus(err) (int32, bool)` in `executor.go`, which
classifies an error from `ex.Send` into an endorsable status: `vm.ErrExecutionReverted` →
`common.StatusEVMRevert` (201, unchanged), `*ExecFailure` → `common.StatusExecFailure`
(460, new), anything else → `(0, false)` (still a hard error: pre-execution rejection or a
genuine non-EVM fault). `runOn`'s fault branch now calls this helper; on a match it builds
`endorsement.ExecutionResult{RWS: state.Result(), Event: <marshaled fault marker>, Status:
status, Message: err.Error(), Payload: ret}` and returns it with **no** Go error — the
same shape the revert branch already used, generalized to cover both outcomes. Both
`Execute` (standalone) and `ExecuteBatch`'s N==1 branch call `runOn`, so this one change
fixes both call sites at once.

**Nonce-bump verification.** Confirmed at the source level: `Executor.ApplyMessage`
(`executor.go` line ~526) calls `core.ApplyMessage`; only a non-nil *outer* error (pre-
execution rejection) triggers `state.RevertToSnapshot`. A non-nil `result.Err` (revert or
fault) is the *committed* path — geth already bumped the nonce and deducted gas before
running the message, and that mutation stays in `state`. Since `runOn`'s fault branch
builds the endorsement from `state.Result()` — the *same* state the faulted message ran
against — the nonce bump is necessarily included. This is asserted empirically by the new
test `TestExecuteBatchExecFailureDoesNotAbort` (see below): it decodes the failing tx's own
`RWS.Writes` for `accKey(addrF, "nonce")` and checks the value decodes (via `bytesToUint64`)
to `1` (bumped from the ledger's `0`).

**Fabric envelope carry-through.** Read `fabricx.EndorsementBuilder.Endorse`
(`fabric-x-sdk@.../endorsement/fabricx/builder.go`): `Response.Status`, `.Message`, and
`.Payload` are passed through from the `ExecutionResult` unconditionally, and the RWS is
*always* marshaled into `Payload` (as an `applicationpb.Tx`) regardless of status. So the
nonce bump is not an artifact only visible inside this package — it rides through the
signed proposal response exactly the way a revert's RWS already does.

**`chain.go` status mapping (also verified, no code change needed).** For the merged-batch
path, `ConvertToDomain`'s per-sub-tx `status` byte is computed as `status := uint8(0); if
tx.Valid && outcome.Status == fc.StatusOK { status = 1 }` — any non-200 status (201 or 460)
already maps to receipt status `0`. For the legacy single-tx path, the byte is computed
from `!fc.IsRevertEvent(tx.Events)`; `IsRevertEvent` checks for a fixed `EventName` prefix
that `common.MarshalRevert` sets unconditionally, so an ExecFailure's event (built via the
very same `MarshalRevert` call in the fixed `runOn`) is indistinguishable in shape from a
revert's and is also treated as non-success (receipt status 0). Both paths were confirmed
correct with no changes required to `chain.go`'s status-byte logic itself (only the
*exclusion* check needed a change — see I1(b) below).

## FIX M2: align N==1 with N>1 on TxRejected (exclude, don't abort)

**Problem.** `ExecuteBatch`'s N==1 branch returned the bare error for a `*TxRejected`
(e.g. a lone nonce-too-high tx with no batchmate present yet), while the N>1 authoritative
loop already excluded `*TxRejected` without aborting. A single pending tx that happened to
be alone in the batch hit a code path with different (worse) behavior than the same tx
would get if a second tx were present.

**Fix.** `batch_executor.go`'s N==1 branch now mirrors the N>1 branch: on `*TxRejected` it
returns `[]endorsement.ExecutionResult{excludedResult(rej)}, nil` (no error) instead of
propagating the error. Folded into the same edit as I1(b) below because both needed the new
shared `excludedResult` helper.

## FIX I1(a) (Important): short-circuit an all-excluded batch in the gateway executor

**Problem.** `gateway/core/executor.go`'s `executeCycle`, after calling
`EndorsementClient.ExecuteBatch`, went straight to `committerTxID` → `SubmitFabricTx` →
`awaitCommit` even when `included` was empty (every drained tx excluded, e.g. a lone
nonce-gap tx with no filler). This wastes a Fabric round-trip on an empty committer tx and,
since nothing ever gets removed from the pending pool, tight-loops on `backoff` (or, before
this fix, actually errored and looped via `backoff` — see the RED-mode trace below).

**Fix.** After the (now 4-value) `ExecuteBatch` call and the unconditional terminal
eviction (I1(b)), `executeCycle` checks `len(included) == 0` and, if so, calls the new
`waitForWork(ctx)` helper (factored out of the pre-existing empty-pool early-return) instead
of falling through to submission. `waitForWork` blocks on `ctx.Done()` or `g.arrivals`,
exactly like the empty-pool case — no busy-spin, no wasted submission, and it naturally
wakes up as soon as a filler tx arrives via `AddPending`/`SendTransaction`'s existing
non-blocking signal.

## FIX I1(b) (Important): evict terminally-excluded txs; keep retryable ones pending

**Problem.** The endorser's exclusion path (`excludedResult`, formerly inlined) tagged
every pre-execution rejection with the same `common.StatusTxRejected`, with no way for the
gateway to distinguish "nonce too high — wait for the gap to fill" (retryable) from "nonce
too low — this exact tx can never land, ever" (terminal). A terminally-excluded tx would
sit in the pending pool forever, re-drained and re-rejected every single cycle.

**Fix — new status constant (`common/proposal.go`).** Added
`StatusTxRejectedTerminal int32 = 410` alongside the existing `StatusTxRejected = 400`
(retryable), and a helper `IsExcludedOutcome(status int32) bool` (`== 400 || == 410`) for
callers that need "was this sub-tx excluded at all" without caring which kind.

**Fix — source-side classification (`endorser/execution/batch_executor.go`).** New shared
helper:
```go
func excludedResult(rej *TxRejected) endorsement.ExecutionResult {
	status := common.StatusTxRejected
	if errors.Is(rej, core.ErrNonceTooLow) {
		status = common.StatusTxRejectedTerminal
	}
	return endorsement.ExecutionResult{Status: status, Message: rej.Error()}
}
```
`core.ErrNonceTooHigh` and insufficient-funds errors never match `errors.Is(rej,
core.ErrNonceTooLow)`, so they correctly default to retryable (400). Both the N==1 and N>1
exclusion branches now call this helper instead of hand-building the sentinel result.

**Fix — gateway-level threading (`gateway/core/endorse.go`).**
`EndorsementClient.ExecuteBatch`'s signature grew a fourth return value:
`(sdk.Endorsement, included, terminal []*types.Transaction, error)`. The old `includedTxs`
helper was replaced by `classifyBatchOutcomes`, which walks the decoded `[]PerTxOutcome`
and buckets each tx into `included` (default: anything not excluded — success, revert, or
ExecFailure), `terminal` (`StatusTxRejectedTerminal`), or neither (`StatusTxRejected`,
left pending). The no-payload fallback (bare/test response) still treats everything as
included with an empty terminal set, preserving prior behavior when there's nothing to
decode.

**Fix — executor wiring (`gateway/core/executor.go`).** `executeCycle` now does, right
after `ExecuteBatch` returns and before checking `included`:
```go
if len(terminal) > 0 {
	g.pending.Remove(hashesOf(terminal))
}
```
This eviction is unconditional — it does not wait for the batch's commit/abort outcome,
because the exclusion reflects ledger state from *before* this cycle's batch ran and holds
regardless of what the rest of the batch does. `included` removal is unchanged (still
happens only after a valid commit).

**Regression guard: `TestBatchMergedCommit`'s nonce-gap subtest.** Traced through
`integration/batch_test.go`'s `"nonce_gap_excluded_until_predecessor_commits"` subtest
against the new code: the lone nonce-too-*high* tx is `errors.Is(rej, core.ErrNonceTooLow)`
== false, so it classifies as retryable (400), lands in neither `included` nor `terminal`,
and stays pending — exactly as required. Ran it directly (see Verification below); it
passes, including under `-race`.

- `ExecuteBatch` returns **no error** and 3 results.

- The other two txs still succeed (`Status == 200`); tx3's write reflects tx1's delivery via
  the overlay (same pattern as the existing `TestExecuteBatchExcludesNonceGap`).
- `MergeResults` on all three yields a merged RWS containing A's and B's/C's writes *and*
  F's nonce-bump write.

**RED verified**: temporarily restored `executor.go`'s pre-fix `runOn` (`git show
HEAD:... > executor.go`) — the test failed with `ExecuteBatch must endorse an ExecFailure
as a committed outcome, not abort the batch: invalid opcode: INVALID`, i.e. `ExecuteBatch`
returned the bare Go error exactly as the bug predicts.
**GREEN verified**: restored the fix; test passes; full suite re-confirmed green.

### 2. `gateway/core/executor_test.go` — `TestExecutorAllExcludedDoesNotSubmitOrSpin` (I1a)

### 3. `gateway/core/executor_test.go` — `TestExecutorTerminalExclusionEvictedRetryableStays` (I1b)

3 pending txs; stub reports `[StatusOK, StatusTxRejectedTerminal, StatusTxRejected]`. Two
assertion phases:
- **Immediately** after `ExecuteBatch` returns (before any commit notification, captured
  via `runCycleAndCapture`): the terminal tx (`txs[1]`) is *already* evicted
  (`g.pending.Len() == 2`), while the included tx (`txs[0]`) and the retryable tx
  (`txs[2]`) both remain pending — proving eviction is unconditional, not gated on commit.
- **After** a `Status_COMMITTED` notification: the included tx is now also removed
  (`g.pending.Len() == 1`); the terminal tx stays evicted; the retryable tx still stays
  pending.

**RED verified**: same pre-fix revert as test 2. First assertion failed:
`expected: 2, actual: 3` (terminal tx wasn't evicted — old `includedTxs` had no concept of
"terminal" and defaulted anything not exactly `StatusTxRejected` into `included`, so it sat
pending like a normal included tx and was only removed on commit — matching the described
bug where a terminal exclusion leaks forever if commit never arrives, and even here shows
up as "not evicted early").
**GREEN verified**: restored the fix; test passes.

## Self-review

- **C1** correctly distinguishes "committed but faulted" (revert, ExecFailure — no error,
  endorsed) from "never committed" (`*TxRejected`, genuine server fault — still an error).
  The classification lives in one place (`committedFaultStatus`) shared by both the
  single-tx and N==1-batch code paths, so they cannot drift apart.
- **M2** is a minimal, symmetric change: N==1 now does exactly what N>1 already did for
  `*TxRejected`.
- **I1(a)**'s `waitForWork` reuses the exact blocking pattern the empty-pool case already
  used, so no new concurrency primitive was introduced — same non-blocking arrival signal
  (`g.arrivals`, buffered size 1), same lost-wakeup risk profile as before (accepted,
  pre-existing, and bounded to at most one extra idle iteration).
- **I1(b)**'s terminal/retryable split is a pure additive classification: `StatusTxRejected`
  (400) keeps its old meaning and old value; `StatusTxRejectedTerminal` (410) is new. Any
  code that only checked `== StatusTxRejected` and forgot about 410 would silently treat a
  terminal exclusion as "included" — I grepped for every reader of `PerTxOutcome.Status` /
  `.Status ==` comparisons against these constants and confirmed `chain.go` (via the new
  `IsExcludedOutcome`) and `endorse.go` (`classifyBatchOutcomes`) are the only two, and both
  were updated.
- Ran `gofmt -l` on every touched file after editing; clean.

## Concerns

1. **Reused revert event marker for ExecFailure.** `runOn`'s fault branch calls the same
   `fxcommon.MarshalRevert` helper for both a revert and an ExecFailure, so the *legacy
   single-tx* path (`IsRevertEvent`-based) cannot distinguish which one happened just from
   the event shape — it only knows "not a plain success." This is harmless today (both map
   to receipt status 0), and the batch path already carries the real status separately via
   `PerTxOutcome.Status`, but if a future feature needs the *single-tx* path to distinguish
   revert-with-reason from a bare EVM fault (e.g. for a JSON-RPC error message), it would
   need either a second marker or to thread `PerTxOutcome`-style status through the legacy
   path too. Flagging this as a known, accepted simplification rather than a defect.
2. **`StatusTxRejectedTerminal` is nonce-too-low only, currently.** Insufficient-funds and
   bad-signature rejections both default to retryable (400), same as nonce-too-high. Bad
   signature is arguably also terminal (a malformed/unsigned tx will never become
   well-formed by waiting), but the task brief scoped I1(b) specifically to "nonce too low
   is terminal, nonce too high stays retryable," so I did not extend the classification
   beyond that without being asked. Easy to extend later if desired (`excludedResult` is
   the single choke point).
3. Did not run the full unfiltered `go test ./...` across the whole module (only the
   packages named in the task's verification commands, per the brief) — the module-wide run
   would also hit the same pre-existing environment-gap failures documented above.
