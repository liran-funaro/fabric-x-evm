Summary

The fix works at the operating point; a batch-size floor remains on conflict-heavy traffic. At the chosen operating point (batch size 1024) both workloads commit 20000/20000 with zero rollbacks and the pipeline is a throughput win: synthetic 1.26× (5,148→6,462 tx/s) and historic 1.25× (5,752→7,206 tx/s). Across the full batch-size scan the pipeline wins on synthetic at every size (1.17–1.49×) and on historic at every size ≥ 512 (1.04–1.28×).

The limit. On the historic USDC trace — a handful of hot accounts touched by nearly every transaction — the pipeline still livelocks below batch size 512 (bs=128: 975/20,000 committed, 2,682 rolled-back batches, 16 tx/s; bs=256: 2,113/20,000 committed, 1,550 rolled-back batches, 34 tx/s). This is the documented depth-1 residual: the fix defers a committed batch's writes and replays its warm-write snapshot for exactly one boundary, which covers auth(N+1). When batches are small, a hot key written by batch N can be skipped by N+1 and read by N+2 — two boundaries later — so auth records a read-version that no longer matches committed state and the committer aborts, cascading into the livelock. At bs ≥ 512 the historic hot accounts are dense enough that every batch rewrites them, keeping each conflicting read inside the depth-1 window. Synthetic has no cross-batch hot-key conflict and is clean at every size.

Methodology

Each data point runs the full stack (orderer, committer/query-service, endorser, gateway) on a 32-core EC2 host and replays a fixed 20000-transaction window of the workload, folding EVM txs into merged committer txs of the stated batch size. The serial path (control) runs the warm and authoritative passes back-to-back; the pipelined path overlaps warm(N+1) with auth(N) behind a barrier, with auth reopening a fresh committed view and replaying the warm pass's in-flight writes. Warm-pass concurrency is held at the code default (one worker per tx in the batch). The correctness gate for every point is 20000/20000 committed with 0 rolled-back batches; a point that misses it is reported as a failure (red row), never tuned away or excluded. The two datasets are reported separately and never consolidated into a single number.

Mechanism — how auth stays correct and fast under MVCC conflict

The pipelined executor launches warm(N+1)'s concurrent cache-priming pass at the top of the iteration, before batch N's optimistic writes are applied to the shared cache. So warm(N+1) legitimately reads a snapshot one batch of writes in the past — for a hot key it sees the value an in-flight predecessor wrote, pinned at that predecessor's spec version.

In the naive pipeline the authoritative pass trusted that stale warm read: it recorded warm's one-batch-old read-versions on hot keys, so when the committer validated batch N+1 against committed state the versions no longer matched and it aborted. The executor rolled the aborted txs back and re-warmed against a still-stale snapshot — the rollback livelock that collapsed historic throughput on every batch size before the fix.

The fix restores the invariant that auth is authoritative, up to one batch boundary. Before the authoritative pass, auth(N+1) reopens a fresh view of the latest committed state (sharing warm's read cache), so any key not in flight is read at its current committed version. Hot keys an in-flight predecessor wrote are read from the in-flight write-cache (held one boundary past commit) or a frozen per-batch snapshot of the warm-pass write-set. Either way auth(N+1) reads batch N's writes at their true (committed) version — never warm's stale one — so recorded read-versions match and no abort results. For reads that stay within this one-boundary window the pipeline is identical in effect to serial.

The residual and the batch-size floor. The deferral and the snapshot both extend exactly one boundary (matching prefetch depth 1), so they cover auth(N+1) but not a hot key written by batch N, not rewritten by N+1, and read by N+2 — two boundaries later. By then N's writes are evicted and its snapshot retired, so auth(N+2) reads from the query view at a version that can be stale relative to the version the committer validates against, and aborts. On historic this gap opens only when batches are small: at bs ≤ 256 the hot accounts are not touched in every batch, the N→N+2 straddle occurs, and the abort cascade returns (bs=128: 975/20,000 committed, 2,682 rolled-back batches, 16 tx/s; bs=256: 2,113/20,000 committed, 1,550 rolled-back batches, 34 tx/s). At bs ≥ 512 the hot set is rewritten every batch, every conflicting read lands inside the depth-1 window, and the pipeline commits cleanly and wins. So the fix raises the correctness floor to bs ≥ 512 on conflict-heavy traffic rather than removing the livelock unconditionally. The authoritative phase where it does commit is I/O-cheap — measured auth read-time is a few milliseconds, matching serial.

Parameter scan 2 — warm-pass concurrency

Why this parameter: the warm pass primes the per-view read cache concurrently before the serial authoritative pass. Too few workers under-overlap I/O; too many add EVM-construction and GC churn. We confirm the code default (warm workers = batch size) is at/near the throughput knee under the pipeline. This scan is run on the synthetic workload only, where the pipeline commits cleanly at every batch size; the warm-worker knee is a conflict-free property the auth read-layering fix does not move. The historic operating point is governed instead by the batch-size correctness floor (see the batch-size scan), not by warm concurrency.

Conclusion

At production batch sizes (bs ≥ 512) the auth read-layering fix eliminates the historic livelock and makes the warm/auth pipeline a correctness-neutral throughput win on both workloads measured: historic 1.04–1.28× and synthetic 1.17–1.49×, and at batch size 1024 both commit 20000/20000 with 0 rollbacks (historic 1.25×, synthetic 1.26×). This corrects the earlier characterization that the historic pipeline is fundamentally slower than serial — at these batch sizes it is faster, and the fix makes auth reopen a fresh committed view and replay the warm pass's in-flight writes at their true version instead of trusting warm's stale reads.

The limit is real and must not be papered over: on conflict-heavy traffic the depth-1 pipeline still livelocks below batch size 512 (128 and 256), because a hot key written by batch N and read by N+2 without an intervening rewrite falls outside the one-boundary coverage. Recommendation: Gateway.Pipelined stays off by default; enable it only with bs ≥ 512 (which the default max-batch-size = 1024 already satisfies), and prefer the serial path — the control, correct at any batch size — when batch size cannot be guaranteed. Extending the deferral depth would lower the floor but yields no throughput gain at production sizes.
